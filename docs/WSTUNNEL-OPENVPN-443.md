# Makia WStunnel 443 — OpenVPN over WebSocket/TLS

## What it is

Makia 1.6.x provides two WStunnel modes; the current stable line is 1.6.3:

- **WStunnel 443 / OpenVPN over WebSocket/TLS** — introduced in 1.6.0 and hardened in 1.6.3.
- **WStunnel WG / WireGuard over WSS** — the older Makia mode, retained separately.

The new mode follows the same transport idea commonly called **OpenVPN over WebSocket**: OpenVPN traffic is carried inside a WebSocket/TLS connection that looks like ordinary HTTPS transport on TCP/443. It is not a claim of compatibility with any third-party proprietary client.

## Architecture

```text
Makia Windows Connector
  → wstunnel client
  → 127.0.0.1:11941
  → WSS/TLS to panel-domain:443/<secret-path>
  → Nginx HTTPS/443
  → 127.0.0.1:10445 WebSocket bridge
  → makia-openvpn-wstunnel
  → 127.0.0.1:11940
  → openvpn-server@makia-ws
  → tun-ws / NAT
  → Internet
```

Nginx remains the sole public listener on TCP/443. The new mode does not try to bind another service to 443.

## Security

- Valid Let's Encrypt certificate is required for the selected domain.
- WStunnel client verifies the TLS certificate.
- The public WebSocket path contains a high-entropy secret prefix generated by Makia.
- The WStunnel service listens only on loopback.
- The WStunnel server uses `--restrict-to 127.0.0.1:<backend>`.
- The dedicated OpenVPN backend listens only on `127.0.0.1`.
- OpenVPN still performs its own certificate authentication and `tls-crypt`.
- Each Makia WStunnel user receives a separate certificate identity prefixed internally with `mwst-`.
- A root-only Unix OpenVPN management socket is used for accounting, policy disconnects and concurrent-session enforcement; it is not exposed over TCP.
- Client Platform account enable/disable, expiry and quota are hard-enforced on the WStunnel OpenVPN identity when the artifact is bound to that account.
- Traffic is sampled per OpenVPN session and aggregated into the Client account, avoiding counter-reset errors when concurrent sessions reconnect independently.
- Nginx applies per-IP request and concurrent-connection limits to the secret WStunnel path.
- Revoking a WStunnel user does not revoke an ordinary OpenVPN profile with the same display name.
- No raw OpenVPN WStunnel backend port is opened in UFW.

Treat the client package and private Client Portal access as secrets.

## Server setup

Prerequisites:

1. Makia panel HTTPS is working on a real domain.
2. Let's Encrypt material exists for that domain.
3. OpenVPN PKI is bootstrapped.
4. WStunnel tooling is installed by Makia.

In Admin:

**Network / Ports → WStunnel 443 → Configure 443**

Makia creates:

- dedicated OpenVPN loopback backend: default TCP/11940;
- WStunnel loopback WebSocket bridge: default TCP/10445;
- a managed Nginx WebSocket path under the existing HTTPS/443 server;
- `makia-openvpn-wstunnel.service`.

## Create a user

After the mode is READY:

**Network / Ports → WStunnel 443 → New user**

or open an ordinary OpenVPN access and choose **WStunnel 443**.

Makia stores an encrypted `openvpn_wstunnel` delivery artifact containing:

- `<name>-wstunnel.ovpn`;
- WStunnel client command;
- connection guide;
- structured transport metadata for Makia Windows Direct Connect.

Bind the artifact to the intended **Client Platform account** to apply that account's enable/disable state, expiry and traffic quota. OpenVPN concurrent-session limiting is backend-enforced; static Android WireGuard identities cannot independently enforce a strict per-physical-device concurrency ceiling. The Client Platform device limit protects authenticated portal/native ticket registration. A downloaded static OVPN/WStunnel package is still a portable credential; strict hardware binding would require issuing a separate certificate per physical device and is not claimed in 1.6.3.

The artifact can be bound to a Client Platform account.

## Windows connection

Requirements:

- Makia Windows Full Device Connector 1.6.3;
- OpenVPN executable/client runtime installed on Windows.

The Makia Windows package bundles the pinned WStunnel runtime. Direct Connect:

1. Redeems a one-time device-bound Makia ticket.
2. Starts WStunnel to the secret WSS/443 path.
3. Waits for the local OpenVPN TCP endpoint.
4. Starts OpenVPN with the delivered user certificate profile.
5. Disconnect stops both processes.

## Manual connection

Run the `wstunnel-client-command.txt` command first, then import/open the delivered `.ovpn` file in a compatible OpenVPN client. Keep WStunnel running for the lifetime of the VPN session.

## Android / iOS

Makia 1.6.3 has an Android ARM64 Direct Connect implementation using a separate WireGuard peer carried through WStunnel/WSS on TCP/443. This is not the Windows OpenVPN backend or a proprietary Windscribe client. The Android UAT/debug-signed build exists; a production release-signed APK and real-device/limited-network UAT have **not** been verified. iOS/iPadOS remain PWA/import-only; no native full-device direct-connect claim.

## Diagnostics

```bash
sudo makia-doctor
sudo makia-uat-smoke
systemctl status makia-openvpn-wstunnel --no-pager
systemctl status openvpn-server@makia-ws --no-pager
nginx -t
```

The public socket should remain Nginx on TCP/443. The WStunnel bridge and OpenVPN backend should be loopback-only.
